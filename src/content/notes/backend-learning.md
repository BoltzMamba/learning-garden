## 背景

我在实习期间曾参与开发一个对话式 AIGC Agent：用户在对话里让 Agent 生成图片和视频，Agent 把生成任务交给后台，后台再交给生成服务，结果回来后放回对话里，用户用"点数"付费。生成服务有三种：初版 demo 调用第三方 API（fal）；正式环境的图片交给公司 infra 的 GPU 集群，这部分接口由我设计；视频调用 Wan API。

这套后端要防住两类典型问题。

**正确性**：

- 网络重试导致**重复下单、重复扣钱**；
- 多个请求同时扣点导致**透支**；
- 进程在半路崩溃导致**钱扣了图没到**，或者**图到了消息发了两次**；
- 用户改了需求以后，**旧结果覆盖新结果**；
- 外部服务的通知**重复、乱序或者不可信**：回调发了两次，`running` 比 `succeeded` 晚到，说"成功"了，产物却没写进来。

**容量**：

- 用户集中在深夜的一两个小时里使用，**GPU 和视频 API 都要排队**。提交量不大，但每个任务要占用几十秒到几分钟；
- 产品在快速增长，资源利用率越接近满载，**等待时间越会急剧变长**；
- 在途任务多，**查询状态的请求会远多于提交请求**；
- 视频按秒计费，并发配额和**成本**都有上限。

关于 GPU 怎么排队、怎么调度的问题属于 infra 负责，我负责与其对接的接口：明确的受理或拒绝、可找回的任务、可靠的完成通知，以及据此算账和给用户反馈。但要把接口设计好，就得懂对面的队列是怎么工作的。

当时很多我对于后端缺乏了解，很多实现依赖 ai 完成，带来了很多局限和风险，现在针对这个项目涉及的后端知识进行重新学习。

这个系列只学读懂这套设计需要的三条线：高并发（包括排队与容量）、分布式系统、中间件。数据库迁移、容器、登录安全等内容不在范围内。

## 学习路线

| 阶段 | 主题 | 学完能回答 |
| --- | --- | --- |
| 1 | 并发前置：唯一约束、事务、隔离级别、丢失更新 | "先查再写"为什么在并发下失效 |
| 2 | 高并发控制：行锁、条件更新、死锁、`SKIP LOCKED`、幂等、账本不变量 | 怎么保证不重复扣费、不透支 |
| 3 | 分布式系统：部分失败、租约、防护令牌、对账、事务发件箱、投递语义；回调的去重、乱序和验签 | Worker 挂了怎么办；改数据库和发消息怎么保证一致；外部通知为什么不能直接当事实 |
| 4 | 排队、限流与容量：利特尔定律与利用率、背压、GPU 队列的常见实现（优先级、公平调度、合批）、令牌桶限流、重试退避与熔断 | 高峰期要排多久；为什么查询量比提交量大；队列满了该怎么办 |
| 5 | 中间件：消息队列、Redis、用 PostgreSQL 当队列的取舍、对象存储与签名 URL | 为什么用 PostgreSQL 当任务队列，而不用 Redis 或 MQ |
| 6 | 串起来：把生成链路上的每个机制对应到它防的问题，以及和 infra 之间的接口为什么这样设计 | 完整讲清一次生成请求在后端经历了什么 |

技术栈：PostgreSQL 16、MinIO（兼容 S3 的对象存储）、Python 3.13、FastAPI。
